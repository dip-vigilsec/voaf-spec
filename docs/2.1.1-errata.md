# Spec release 2.1.1: errata candidates

From `NOTES.md`, which is not in this repository: the notes of a session that
implemented a verifier from the spec text alone, against the 2.1.0 draft at
`d42a55f` (revision 4). The 2.1.0 fix round resolved the items its rulings
covered; each line below is an item it left as it was, with its section of
`NOTES.md`. Line numbers are lines of `spec/2.0/preimage.md` at `d42a55f`.

- NOTES 1: The spec maps no verdict to a process exit code, and does not say how a 1.0 document's verdicts, which lines 940-941 keep apart from every 2.x verdict, are named.
- NOTES 2.1: Section 7 names no member for the entries of a 1.x object document; Vigil's 1.0 exporter writes them under `interactions`, which appears only in `neg_relabelled_1_0`, and an entry's own `voaf` there is not mentioned.
- NOTES 2.2: Section 7 does not say whether a 1.x object document without an `interactions` array is walked, or whether the 2.x-only structure line 847 lists is exhaustive, so that a 1.x document carrying `genesis` or `anchor` is not a mismatch.
- NOTES 2.2: Section 7 does not say whether an empty top-level array, which declares no version, is a 1.x document or `unrecognised_format`; the reference verifier reads it as 1.x.
- NOTES 2.3: Section 7 does not say which 1.0 walk a 2.x verifier's link-only mode makes: the README's (entry 0's `prev_hash` is `sha256:` and zeros, each later one the SHA-256 of the previous entry's canonical JSON, over the schema's array of entries, which carry no `hash`) or Vigil's (each `prev_hash` equals the previous entry's stored `hash`, entry 0 not anchored, entries under `interactions`); nor whether line 938's "linkage only" includes the README's recompute or line 68's v1 hash.
- NOTES 2.4: Section 6 gives a store with zero rows under an anchor whose `entry_count` is above 0 two states: line 793 and lines 809-812 make it `lost`, which "is not `truncated`", while line 824 says a copy of the main file with no rows presents as `truncated`.
- NOTES 2.5: Section 6's store table gives one piece of evidence two states: a stored hash at the anchored count that differs from the anchor's head is `broken` when more rows follow (line 797) and `truncated` when the counts are equal (line 799).
- NOTES 2.6: The spec does not say whether a verifier may take the genesis from outside the document, from an install nonce or a known genesis, or which wins when it disagrees with the carried one.
- NOTES 2.8: The spec does not say whether a `chain_upgrade` may appear after `seq` 0.
- NOTES 2.8: "Index" in "at that index" and "break at or before index N" (lines 123, 861 and 933-935) is not defined: a position in the `seq` walk, in the `records` array, or a `seq` value. The reference verifier reports a finding's position in the `records` array, which is not the walk position when the array is out of `seq` order.
- NOTES 2.9: No code is given for a 1.0 entry the link-only walk cannot read (no string `prev_hash` or `hash`), or for raw preimage bytes that do not parse, which only an implementation's own reader meets.
- NOTES 2.12: When `event_kind` names no schema, the spec does not say whether rule 1 still checks the record's other members.
- NOTES 2.12: Envelope fields 1 and 2 (lines 269-270) have no member name, while line 868 makes "any envelope field" that is missing a `missing_field`.
- NOTES 2.12: The spec does not say whether rules 3 and 4 run on a record that failed rule 1.
- NOTES 2.12: The spec does not say whether the 2^24 per-preimage bound applies to a record whose fields do not all decode.
- NOTES 2.12: The spec does not say whether a verifier reports every violation in one record or only the first, as with an array holding several bad elements.
- NOTES 2.12: A 26- or 28-element `features_canonical` is `feature_arity` under rule 2, while line 327's type column reads "array of integer, exactly 27".
- NOTES 2.12: Lines 192-194 say arity drift "surfaces as a hash mismatch", but under rule 1 a record with a missing or extra member fails `missing_field` or `unknown_member` first.
- NOTES 2.13: `-0` is valid JSON, and a parser that converts numbers reads it as 0; lines 118-119 do not say that an integer is read from its literal text, nor do they name a code for it.
- NOTES 2.13: Section 7 does not name a JSON number with a fraction or exponent in an integer field, or `true` and `false` in one, as `wrong_type`.
- NOTES 2.13: Section 3 calls scores `i64` (line 215), while section 2 bounds only the decimal length of an integer (line 142) and section 7 lists no range check.
- NOTES 2.13: A JSON string holding a lone surrogate, such as `\ud800`, has no UTF-8 encoding, and line 123 names no code for a value that does not decode.
- NOTES 2.13: A document whose bytes are not UTF-8 cannot be read record by record, so line 123's "a verification failure at that index" cannot apply to it.
- NOTES 2.13: Line 122's "no BOM" does not say whether a document that starts with a byte-order mark is rejected, nor does section 7 say whether nesting too deep to parse, a lone surrogate or a number outside the binary64 range, anywhere in the text and in members it ignores too, is `invalid_json`; the reference verifier's parser rejects all three.
- NOTES 2.13: The parse check does not say that member names are compared after JSON unescaping, so that `"decision"` and `"d\u0065cision"` repeat a name.
- NOTES 2.13: Lines 45-46 say revision 4 forbids a repeated member name "inside a record", while section 7 rejects one at any depth, the top-level object included.
- NOTES 2.13: The spec does not describe reading a preimage back field by field; an implementation's reader of raw preimage bytes enforces the section 2 payload rules and checks each header before its payload.
- NOTES 2.14: Lines 127-130 say a verifier does not validate the shape of a hash-valued field, while lines 134-135 say such fields are hashed as their 64 lowercase hex bytes and line 272 types `prev_hash` "string, 64 lowercase hex".
- NOTES 2.14: The spec does not say that the stored hash, `prev_hash`, the genesis and `head_hash` are compared as exact strings, so that an uppercase `prev_hash` is a `link_break` though its own record verifies.
- NOTES 2.15: Lines 44-45's "with anything written beside it" reads as the condition for rejecting the directive, while lines 422-427 reject any directive in a document, a bare one included. The "before hashing" wording is the NOTES 3.9 item.
- NOTES 2.16: Positive vector records carry no `hash` (line 1033), so rule 1's `missing_field` for `hash` would reject them; section 8.1 does not say that a loader decodes them without that requirement (line 1035 already makes `expected_hash` their stored hash in the chain walk).
- NOTES 2.17: The spec does not say that the producer rules of sections 4.4, 4.4.1 and 4.7.1 (`held_ms` 0, the NULL hashes of `connection_panicked`, the differing hashes of `shutdown_deny`) are not verifier checks.
- NOTES 2.17: The spec does not say that content against its digests (`_sha256`, `_length`, `_truncated`, the NULL-together rules) and the section 3 slot rules are not verifier checks.
- NOTES 2.17: The spec does not say that cross-record rules (`id` and `gate_id` uniqueness, `interaction_id` naming a record, a `chain_truncation` record's counts against its position, the predecessor patterns of a `chain_upgrade`) are not verifier checks.
- NOTES 2.17: Lines 690-693 make `protection_on` and `protection_off` evidentiary for time gaps but give no threshold and no output.
- NOTES 2.17: Line 604 ("Normative, and the token table below wins over any attribute") and line 680 ("`event` is one of") read as closed vocabularies, while rule 2 makes an unknown token, other than an `event_kind`, not a failure.
- NOTES 2.17: Rule 2's allow rule (lines 903-909) does not say whether a record with a finding, or the record before a `link_break`, may be counted or presented as an allow, or how many unrecognised pairs a verifier lists.
- NOTES 2.18: Line 911's MUST escape gives no escaping form, and no bound on the length or nesting of a document value a verifier shows.
- NOTES 2.20: The revision 3 over-limit cases, `neg_content_over_limit` and `neg_array_over_limit`, read either as a document field long enough to need the header or as raw preimage bytes carrying it; line 1048 does not say which.
- NOTES 2.21: Lines 382-383 set `_truncated` "whenever the full content exceeded the cap", while lines 436-438 store a body that is not UTF-8 with `_truncated` false whatever its size.
- NOTES 2.21: Appendix A.4 (lines 1197-1198) says `app_version` appears on "a `lifecycle` `shutdown` record", while section 4.7b (lines 676-678) makes it a non-nullable field of every `lifecycle` record.
- NOTES 2.21: In lines 802-803, "This is the fourth badge state for Track B, recorded as a `chain_truncation` event when the chain resumes", "This" may mean `empty`, `lost` or `truncated`.
- NOTES 2.22: Line 1051 does not say where a record-form negative sits in a chain: alone, or in place of the chain record with its `seq`.
- NOTES 2.22: The spec bounds neither the findings a verifier keeps nor those it lists, so a large document of malformed records produces millions; the verdict depends only on the codes.
- NOTES 3.3: `interaction_second_conversation`'s note says "Identical to interaction_full_nonascii except conversation_ref", but `id` differs too, so the vector does not isolate `conversation_ref`.
- NOTES 3.5: Five interaction vectors carry `execution_gate_id` `"gate-9"`, a field lines 368-370 say no producer writes yet, and no note says the value is hypothetical.
- NOTES 3.6: `held_ms` 14320, 2150, 6100 and 9400 are not whole seconds times 1000, which appendix B (line 1251) says Vigil 2.3.2 writes, and no note marks the departure.
- NOTES 3.7: `chain_truncation` at `seq` 10 records `observed_entry_count` 12 and `observed_head_hash` `ffff...`, which also disagree with its own position: ten records precede it, and the stored hash at `seq` 9 is `eeced3a5...`.
- NOTES 3.8: `lifecycle_shutdown`'s note says "the anchor and the chain head are the same event", but in the file's chain the head is `lifecycle_protection_off` at `seq` 12; the 2.1.0 fix round corrected the same sentence in section 4.7b and left the note.

## From the update at `08f06db`

The same session updated its implementation to `08f06db`, now in
`conformance-py/`, with its `NOTES.md`. These items are new there. Line numbers
in this section are lines of `spec/2.0/preimage.md` at `08f06db`.

- NOTES 2.3: Section 7 still does not say whether an empty top-level array is a 1.0 document with no entries or a document that declares nothing. Line 867 rejects "a top-level value that is neither an object nor an array of entries each declaring 1.x", which `[]` vacuously is, and line 1126 fails a 1.0 array "in which an entry does not declare 1.x", of which `[]` has none. The NOTES 2.2 item above was about the `d42a55f` text; the new wording leaves it open. `conformance-py` reads `[]` as a 1.0 document with no entries.
- NOTES 2.10: The record count is "the number of elements of `records`" (line 889), but the head check reads "position `entry_count - 1` of the walk" (lines 1002-1004), and "a record with no integer `seq` has no place in the walk" (lines 1028-1029). Section 7 does not say whether that position counts records outside the walk, or what happens when it falls past the walk's end. `conformance-py` counts walk positions only, and skips the head check with a note when the position is past the end; such a document is already `broken` by rule 1.
- NOTES 2.11: Two MUSTs have no code: the report "that truncation of the chain's tail cannot be detected from this document" (lines 1013-1014) and the "unanchored tail of N records" (lines 1007-1009). Section 7 says neither how they are reported nor that they stay out of the codes a document reports, which `negative_documents[].expected_codes` (line 1252) implies by listing neither.
- `entry_count` is read exactly "in any notation (`13`, `13.0` and `1.3e1` are one count, and a count of 2^64 or more exceeds every record count)" (lines 898-900). A verifier must therefore compare a literal such as `1e1000000000`, or a run of a million digits, against the record count without materialising its value. Converting to an integer costs time and memory in the size of the value, and a decimal library can fail outright on a large enough exponent: Python's `decimal` raises on `1e9999999999999999999`. A negative exponent needs the same care: `1e-1000000000` has to be found not to be an integer. Consider bounding it. Two ways:
  - Say that the value is decided from the literal's significant digits and exponent alone. A value of 2^64 or more exceeds every record count without being computed. An exponent too long for a 64-bit integer decides by its sign: a positive one exceeds every record count, and a negative one is not an integer unless the significand is zero.
  - Limit `entry_count` to a literal of at most a fixed number of characters, with a longer one `anchor_unreadable`. This also needs an exponent bound, because a short literal can carry a huge exponent.

  `conformance-py` does the first. It decides by digit count and exponent length, and treats any value of more than 40 digits as exceeding every record count.
